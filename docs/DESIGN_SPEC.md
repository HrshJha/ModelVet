# Developer experience and product interaction design

Status: local CLI interaction implemented; no dashboard is in scope. `CLI_SPEC.md` is the normative command grammar; this describes interaction design and examples.

## Design principles

1. **Evidence before verdict:** show applicable checks, omissions and uncertainties before allowing a reviewer to interpret `APPROVE`.
2. **Human + automation:** same semantic result via JSON, Markdown, console; stable documented exits; no prompting in CI.
3. **Safe defaults:** only local artifacts, no untrusted model execution, no surprise network, no directory writes inside input.
4. **No false confidence:** distinguish no findings, skipped, failed, unsupported and not run in both text and machine output.
5. **Inspectability:** every key finding shows file ID, check, source tool+version and raw evidence digest/path or explanatory limitation.
6. **Honest scope:** include a prominent `Static checks only; model loading not tested` limitation for MVP.

## Interaction hierarchy

Primary: `modelvet scan PATH`; review: `modelvet inspect REPORT.json`; health: `modelvet doctor`; policy: `modelvet policy validate`; help/version standard. CLI error path must never depend on Unicode icons, color, or animations. Use short, scannable text sections and full details in report files.

## Screens / layouts (illustrative, not generated by running app)

```text
ModelVet — local artifact assessment (planned)
Artifact: sha256:123...    Input: [redacted]
Decision: INSUFFICIENT (exit 30)
Mandatory check coverage: 3 complete, 1 skipped, 1 unsupported
Reasons:
  - modelscan:weights.pt: inner serialized member not confirmed inspected
  - format:custom.bin: unsupported security-relevant data
Reports: /user-chosen-output/<artifact>/<run>/report.json, report.md
Limitations: no model loader invoked; no inference backdoor testing
```

Console must never say `SAFE` for APPROVE; say `policy criteria satisfied (scope: local static checks)`.

## Report navigation

Markdown order: `Decision and scope` → `Identity and toolchain` → `Required coverage gaps` → `Corroborated findings` → `Reported/unverified findings` → `Claims and conflicts` → `Policy rule trace` → `Resources/limitations` → `Reproduction instructions`. JSON fields per `DATA_MODEL.md`. Long raw scanner errors truncated in display but digest/full bounded payload retained in secure raw folder.

## UX state handling

| State | Human view | Machine view | User action |
|---|---|---|---|
| All checks complete/no prohibited findings | APPROVE plus scope caveat | 0 | proceed only under local policy |
| Conditions required | CONTROLS + named controls/owner | 10 | enforce controls before use |
| Verified prohibition | BLOCK with rule IDs and artifacts | 20 | reject under policy |
| Evidence missing/conflicting | INSUFFICIENT + exact unresolved checks | 30 | repair tool, format, or evidence |
| Bad path or invalid TOML | concise explicit error | 40 | fix input |
| Internal failure | error ref, no misleading verdict | 50 | file issue |

## Accessibility / CLI ergonomics

`NO_COLOR=1` plain text; no meaning encoded only in colors; counters with words; stderr/status vs stdout structured JSON separation; `--quiet` for pipelines; deterministic ordering of findings by severity/category/path/check ID; preserve Unicode filenames but escape control characters; output path shell quoting in documentation; avoid dumping large raw reports to terminal. Help text must include risk disclaimer and exit code table.

## Config management

Default policy is embedded and reviewed; command flags override allowed presentation/limits, not silent security reductions. `--policy` requires a TOML with `policy_id`, `policy_version`, mandatory check rules and format applicability; validator rejects unrecognized fields. Future user policy examples in `examples/` are not yet created.

## Output directory and reproducibility

Never generate files inside the inspected directory, as that would change identity. Generated `report.json` and `report.md` include run ID/time separately from canonical semantic digest. If two scans see identical snapshot bytes and same tool versions/configuration/results, semantic digests match; wall times may not. Report directories are non-overwriting, mode 0700 where supported.

## No web UI in MVP

A dashboard adds authentication, storage, browser sanitization and operational risks without helping prove the core hypothesis. Revisit only if a real repeat-review workflow requires report browsing; first demonstrate meaningful coverage findings through CLI and benchmarks.

## Journey acceptance checks

For each `scan`, `inspect`, `policy validate`, `doctor`, `version`: verify interactive and `CI=1` output; on success and failure show exact source of decision; verify JSON parseability with `--json-summary`; no prompts; errors on stderr; no untrusted code loaded; preserved policy/version/identity. Tests `T-CLI-01`, `T-E2E-01`, `T-REPORT-01`.

## Proposed primary Hub journey — PH-19/20

The next proposed CLI experience is `modelvet scan https://huggingface.co/owner/model-name --revision <ref>`; the existing directory argument remains secondary and backward-compatible. The UI remains optional and is not expanded to remote scanning by this proposal. User-facing stages must be truthful and ordered: validate reference → resolve immutable revision → inventory → selected retrieval → local checks → coverage/policy → report. Show the resolved commit and list omitted/unsupported/unavailable files. Only display retrieved/assessed after that exact step completed; decision is independent and may be any of four states.

Public URL requires no secret. Private/gated repositories show an actionable local-authentication message without prompting or exposing credentials. Never offer “collect all API keys.” Each retrieval limit and skipped file is visible; recommended next actions cannot silently widen fetch scope or synthesize checks. Full interaction/errors/limits are in `HUB_ASSESSMENT_SPEC.md` and proposed CLI syntax in `CLI_SPEC.md`.
